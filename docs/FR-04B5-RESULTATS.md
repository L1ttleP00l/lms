## 2. Annonces : sous-lot de présentation

Les fragments « A new … published on » + marque + « that might interest you » deviennent une phrase gettext complète avec {0}. Salutation existante Hello Learner → Bonjour, Here are the details → Voici les détails. Boutons source View the course/View the batch → Consulter le cours/Consulter la session. Aucun titre, description, nom de marque ou formateur n’est traduit.

Session : phrase complète `From {0} to {1}`, date unique si end_date absent ; date longue et heure courte natives FR/EN, même timezone de présentation. Aucun horaire/date/fuseau stocké ou instant modifié. La modalité medium est toujours transmise brute mais n’était et n’est pas affichée dans ce template : aucun champ ajouté pour ce lot.

**Régression réelle sans image** : avant correction, rendu Jinja natif échoué avec `ValueError: empty separator` sur `full_name.split("")`. Les deux templates utilisent maintenant `(full_name or "")[:1] | upper | e`. Le test des deux variantes réussit, sans modifier les données du formateur. Avatar décoratif alt vide, nom adjacent conservé ; alt du logo = marque échappée ou Logo traduit.

**Contrat de destinataires défectueux préexistant** : get_instructors retourne des dictionnaires `_dict` (name, username, full_name, user_image, first_name, bio), utiles au template. Les annonces passent cette même liste à recipients. `QueueBuilder.recipients` applique set(emails), qui lève `TypeError: unhashable type: '_dict'` pour notre formateur fictif. Diagnostic exécuté sans queue ni réseau. Si la liste est vide, ce défaut précis n’est pas démontré ; aucune généralisation à tous les envois. **Pas de conversion automatique vers name/email**, car elle modifierait le contrat effectif de diffusion et nécessite une décision distincte. Les tests de rendu interceptent sendmail avant ce traitement et ne prouvent donc pas la livraison des annonces.

Tests publics homogènes FR, homogènes EN et mixtes : un contenu reste celui du contexte actif. Un public EN peut ainsi recevoir du français si le contexte est FR. Un appel sendmail par objet conservé ; To contient les mêmes objets formateur et BCC les mêmes identifiants activés, CC absent. **Pas de promesse de langue individuelle.** Le Framework peut préparer plusieurs queues selon queue_separately/volume, donc un appel applicatif n’équivaut pas à une garantie d’une queue ou d’une Communication réelle.

## 3. Emails individuels

### Cours disponibles

Le code historique préparait « titre is available! », puis enqueued frappe.sendmail avec template/args : le corps était rendu plus tard dans la langue du job. Une portée print_language autour du seul enqueue aurait été insuffisante.

Le même enqueue vise désormais un worker LMS minimal et reçoit l’identifiant utilisateur. Le worker fait `print_language(get_user_lang(recipient_user))`, puis construit **{0} is now available! → {0} est maintenant disponible !**, en-tête HTML échappé et rendu standard natif. Même destinataire, queue courte, timeout, asynchronisme, now=True et nombre de jobs ; aucun filtre, écriture ni tentative supplémentaire. Les args métier restent bruts. La phrase auparavant anglaise directe « Click on the link below to start learning. » est maintenant extraite et traduite. Le titre est échappé avant frappe.bold ; premier prénom, marque et liens échappés.

Limites conservées : email_sent est marqué après enqueue, **pas après livraison** ; pas d’atomicité ou stratégie de reprise ajoutée. Les intérêts déjà marqués ne sont pas filtrés par cette fonction. Les jobs historiques déjà en attente vers frappe.sendmail ne sont pas transformés rétroactivement. Déploiement/vidage de file non réalisés.

### Mentions

Même collecte d’adresses et même garde, sans déblocage d’emails jusque-là empêchés. Association `zip(mentions, recipients, strict=True)` sur deux listes de même longueur issue de la compréhension existante ; aucun saut, ajout ou déduplication. La langue se résout avec l’identifiant de mention. Test avec adresse de livraison différente : préférence FR/EN correctement appliquée.

Sujet existant `{0} mentioned you in a comment` traduit ; corps générique **{0} mentioned you in a discussion.**, adapté aux leçons et sessions au lieu de parler systématiquement de batch. Source anglaise et paramètres conservés. Sender/link échappés, en-tête échappé, retry3 et args inchangés. Le contenu `content | markdown` historique est conservé.

Liens : cours/leçon par les mêmes helpers, et session email **/batches/{name}#discussions** historique, distinct du lien portail `/lms/batches/…`. Aucun préfixe corrigé implicitement ; validité de navigation effective de ce lien historique non revendiquée.

### Langue et contexte

Préférence User → langue système → contexte → en, via get_user_lang/print_language natifs. Deux FR/EN traités successivement indépendants, absence de préférence testée avec sites fictifs FR et EN ; contexte initial restauré après erreur du worker/de mention. Aucun User/System Settings modifié. Initialisation préalable du worker non résolu par print_language : comportement natif documenté dans B.4 conservé, pas de nouveau moteur linguistique. Une clé de sujet d’annonce retirée du dictionnaire de test revient à sa source anglaise.

## 4. Notifications persistantes : diagnostic et conception

make_notification_logs natif résout les utilisateurs activés ayant les notifications autorisées, prépare un document par utilisateur et exclut l’auto-notification sauf types prévus ; éventuel dedupe_on natif. enqueue_create_notification peut dédupliquer sa liste, mais les producteurs LMS examinés appellent make_notification_logs directement : ne pas assimiler ces deux chemins.

Le sujet est une chaîne déjà rendue, sans msgid/paramètres/langue permettant une retraduction. Diagnostic natif avec new_doc/insert entièrement fictifs : deux lignes destinataires distinctes, même sujet, aucun métadatum de traduction. Changer le contexte FR/EN ne transforme pas la chaîne stockée. Les producteurs de réponse et mention conservent leurs nombres et destinataires simulés.

API `get_notifications` : for_user forcé à la session, seul read facultatif accepté, dernières50 lignes, détails d’auteur filtrés. Le panneau utilise decodeEntities puis **v-safe-html:basic** (DOMPurify, liste de balises/attributs autorisés) ; aucun `__(subject)` ni clé originale. Liens convertis en routes cours/session, hachage discussions conservé ; marquage lu par méthodes natives, état/counters rechargés. Aucun changement de ces sources/API, statuts, filtres ou anciennes lignes en base. Lecture statique, pas de recette navigateur supplémentaire.

## 5. Diffusion de masse : décision à prendre séparément

Le nombre effectif de queues dépend aussi du Framework/volume ; aucune campagne réelle testée. Le statut `notification_sent` ne doit pas passer à vrai après un premier groupe réussi si d’autres échouent. La présente mission **n’implémente aucune de ces nouvelles stratégies**.

## 6. HTML, contenus et temps

Les descriptions annoncées sont Small Text (batch.description) et texte d’introduction ; titres, descriptions, noms, marque, images et attributs URL sont échappés avec `|e`. Les valeurs brutes restent identiques dans les args. Tests balises, guillemets et esperluettes ; aucun `|safe` ajouté. Pas de refonte de contenu pédagogique riche : le rendu Markdown des discussions est intact et conserve notamment le HTML éditorial `<span>` dans le diagnostic. **Ce filtre Markdown n’est pas une preuve de sanitation générale des emails** ; revue HTML/URLs distincte recommandée. Échappement d’attribut ne signifie pas validation de protocole ou sûreté de toute URL externe enregistrée.

URL d’annonce toujours absolue via get_url(get_lms_route(...)), logo/avatar inchangés ; cours disponible toujours href relatif avec URL complète affichée, mentions inchangées. Aucun téléchargement d’image ni appel externe pour les tests. Identité visuelle/styles inchangés.

Dates FR/EN avec et sans fin ; heure short et date long natives. Limite **reproduite** avec le vrai format_timezone : l’annonce de session fournit seulement start_date, donc l’offset est celui de minuit. Le 28 mars 2027 Europe/Paris, il peut afficher GMT+1 alors que 23:45 est GMT+2. Trois rendus comparés aux 27/28/29 mars ; aucun changement métier pour corriger ce problème hors périmètre. Date/heure stockées et horloge conservées, pas de conversion inventée. Ajouter le bon instant de référence exige une décision et des tests de fuseaux propres.
